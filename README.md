# bloodstrike-dumper

Offset dumper for BloodStrike steam version. Attaches to the running game, snapshots the main module and resolves engine offsets automatically, writing them to `offsets.hpp` next to the executable.

## Usage

Start the game load into the range, then run `bloodstrike-dumper.exe` as administrator.

```
bloodstrike-dumper [options]

  (no options)        attach to BloodStrike.exe
  --process <name>    attach to a different process name
  --file <path>       analyse a PE file on disk instead of a running process
  --no-pause          don't wait for enter before exiting
  --help              show usage
```

Exit codes: `0` every offset resolved, `1` the target couldn't be loaded, `2` some offsets are missing or conflicting.

## Output

```cpp
// Generated by bloodstrike-dumper
// target:    BloodStrike.exe (pid 1234)
// image:     base 0x7FF6A0000000, size 0x94E9000, timestamp 0x6ACBBFBA
// dumped at: 2026-11-07 21:00:00
// live:      fov 90.0, viewport 1920x1080
// resolved:  31/31

#pragma once
#include <cstdint>

namespace offsets {

	// globals
	constexpr std::uintptr_t ClientEngine = 0x80D5980;
	constexpr std::uintptr_t EntityList = 0x8B78AA8;

	// engine
	constexpr std::uintptr_t IGameplay = 0x58;
	...

} // namespace offsets
```

An offset that can't be resolved is written commented out (`// constexpr std::uintptr_t X = ?; // not found`),
so code that uses it fails to compile instead of running with a stale value. If resolvers disagree, the
candidates and where each came from are listed in that comment instead.

## How it works

Signatures are only used to **find** a function. The values themselves are read from the decoded
instructions with [Zydis](https://github.com/zyantific/zydis), e.g. "the displacement of the load through
the register that holds the camera". That survives register reallocation, `disp8`/`disp32` changes and
reordering, which reading bytes at fixed positions does not.

- Most offsets are found by more than one resolver. A value is only reported when all of them agree,
  otherwise it is listed under `conflicts`.
- Python type objects are located from their type name string, without any signature.
- When attached to the game, a live check follows the pointer chain to the camera and prints its fov and
  viewport, so a bad dump is obvious.

## Building

Visual Studio 2026 (v145 toolset), x64. Open `bloodstrike-dumper.slnx` and build, or:

```
msbuild bloodstrike-dumper.slnx /p:Configuration=Release /p:Platform=x64
```

The binary ends up in `bin/Release/`.

## Layout

```
bloodstrike-dumper/
  src/
    pch.hpp               precompiled header (Windows, STL, Zydis)
    main.cpp
    app/                  command line, application flow, live check
    core/                 PE image, process snapshot, byte patterns
    analysis/             Zydis wrapper (Instruction, Disassembler)
    offsets/              offset table, Resolver base class, pipeline
      resolvers/          one file per area: camera, engine, entity, pose, python
    output/               console, offsets.hpp writer
  third_party/zydis/      Zydis 4.1.1 amalgamated (MIT)
```

## Adding an offset

1. Add an `OffsetDefinition` to `kOffsetDefinitions` in `src/offsets/offset_table.hpp`.
2. Derive from `Resolver` in the matching file under `src/offsets/resolvers/`: find the function with
   `find_unique(context, pattern_)`, sweep it with `context.disassembler`, and `record()` what you find.
3. Register it in `ResolverPipeline::standard()` (`src/offsets/resolver_pipeline.cpp`).
